# HYPER EXTRACT architecture

C++20 native Windows CLI and Win32 GUI call one shared archive service. A header probe selects only ZIP / 7z / RAR4 / RAR5; filenames do not select the decoder. The service opens original archives read-only without write/delete sharing.

ZIP: bounds-checked central/local/ZIP64/descriptor parser -> strict encoding conversion -> deterministic PathGuard/DirPlanner -> independent file batches -> per-worker libdeflate fast path or zlib streaming -> common Win32Sink -> bounded asynchronous close queue -> drain. Aggregate logical fast payloads are limited to 512 MiB; reused vector capacity can retain more, subject to the 1.5 GiB process cap. Store copies in 1 MiB chunks. Raw CRC32 and exact compressed consumption/expanded lengths are checked. A single DEFLATE stream is not split into fake parallel tasks.

7z/RAR: dynamically load the adjacent official 7z.dll using an absolute path and restricted DLL search directories. The vendored official IInArchive/IStream SDK headers define the ABI. Query metadata and reject encrypted/split/link/anti/alt-stream/special entries before output. RAR4 POSIX attributes use the upstream 0x8000 marker with Unix mode in the upper word. Callback streams feed the same PathGuard and Win32Sink, track actual length and CRC where exposed, and require all SDK operation results and entries to succeed. Solid decoding remains internal to the official handler. DLL objects are released before unloading the module.

Output transaction: pin plain local ancestors; reserve a random same-volume .hx session; extract into payload under a fresh guarded root; pin planned subdirectories with FILE_LIST_DIRECTORY (attribute-only opens do not enforce sharing as intended); check and drain all close work. Commit with NtSetInformationFile(FileRenameInformation), resolving one destination leaf relative to the pinned parent handle with replacement disabled. A temporary sharing relaxation on the target parent permits Windows' internal rename open while preserving the directory handle identity. No copy fallback silently changes the transaction semantics. The data is closed, not forcibly flushed to physical media.

JobControl uses atomic cancellation and byte counters. CLI throttles progress and wakes its progress thread immediately at completion; GUI uses a timer and a worker thread. The GUI and CLI impose a 1.5 GiB process commit limit through a process-local Windows job. SDK dictionaries above an exposed 512 MiB hint are refused; the process limit also constrains hidden decoder allocations. No Defender/power plan/system cache changes are made.

AutoTune uses fixed-seed synthetic ZIPs, a verified warm-up, randomized paired blocks, per-trial read-back CRC/count verification outside the timer, measured CPU/working-set/queue diagnostics, medians/p90/MAD and paired bootstrap intervals. Quick mode explores eight W/K settings. Full mode uses 10,104 entries / 287,000,000 bytes and selects an affordable candidate subset from measured warm-up cost, including a matching earlier profile. The budget is checked between complete blocks, with at least two blocks; a slow block can exceed the nominal budget. Profiles are bounded strict flat JSON, reject duplicate keys and invalid numeric types, and require an environment fingerprint and workload class match. 7z/RAR calibration and block-level scheduling are not implemented.

Legacy write-only hx-tune sources/tests are retained for history and regression; only hx.exe and HyperExtractGUI.exe are the delivered frontends.
